# Browser performance protocol

The optional localhost `?benchmark=1` integration uses `createPerformanceGame()` from `src/qa/performance.ts`. It is a synthetic rendering workload, separate from normal match verification. It cannot prove resource balance, fair AI, match duration, victory, defeat or player controls.

The fixture contains 100 living units, 50 per faction, with all four unit roles represented on each side. Paired units attack each other near world coordinate `(24,24)`. Their fixture health is 1,000,000, so they remain alive throughout the sample. Explicit attack orders avoid automatic illusion creation. No faction definitions or simulation functions are changed. Both settlements have completed buildings away from the fight and enough capacity for their armies. Starting resources are zero, training queues are empty, and central resource nodes are removed to avoid placing the initial formation inside obstacles. Peripheral deposits remain.

The host must show an explicit benchmark indicator, start the fixture, center the camera at `(24,24)`, and keep all 100 unit sprites inside the camera. Do not issue player commands during the sample. Use the final Blender artwork and record whether it is loaded. Start a new collector only once the scene and artwork are ready. The fixture is designed for the 65-second warmup-plus-sample window, not an indefinite match; restart it for another measurement.

Call `FrameCollector.record(timestampMs, metadata)` once per rendered frame, using a monotonic browser timestamp such as `performance.now()` in Phaser's post-render event. Do not use its smoothed FPS estimate or a fixed timer. The collector excludes a 5-second warmup and measures at least 60 seconds of complete frame intervals. It retains a slow final frame in full and reports the actual measured duration. Average FPS is frame count divided by that duration. Median, p95 and p99 use nearest-rank percentiles of the frame intervals in milliseconds. The collector does not discard stalls or outliers.

For every recorded frame, supply current living, fog-visible and on-screen unit counts. `countPerformanceUnits(state, cameraContains)` calculates the first two and uses the caller's camera predicate for the third. The predicate must account for the rendered sprite bounds or use conservative margins that keep the entire sprite inside the camera; a unit's world coordinate being visible through fog does not prove that its sprite is on screen. Also record CSS viewport size, canvas display size, drawing-buffer size, device pixel ratio, document visibility and final-art readiness. A completed sample is invalid if a unit count departs from 100, art is missing, the page is hidden or dimensions change. A validity flag means the workload conditions held; it does not mean the 60 FPS target passed.

Use a 1920×1080 browser viewport for the requested 1080p comparison, and report the canvas dimensions separately because the HUD occupies part of the viewport. Keep zoom and camera position unchanged. Capture the browser and GPU information alongside the exported summary. Run the production build in a foreground browser window. For the Codex in-app browser, also check the browser visibility capability and set it visible before measurement: document.visibilityState can report visible while the browser panel is hidden. Record both observations. If a background tab, external load or a browser automation attachment affects the result, record that limitation and repeat under the intended conditions.

Report the full JSON summary and a screenshot of the workload, including its indicator. State the measured average FPS and frame-time percentiles rather than rounding a slower result to 60 FPS. Repeat the sample to check variability before claiming the target is met. This module has no browser interactions and does not itself establish measured browser performance.

The implemented collector rejects a paused simulation and requires 1920×1080 for viewport, canvas CSS size and drawing buffer. Final-art readiness requires every declared texture/frame to load and 100 successful living-unit sprite draws in each sampled frame. The partial-art instrumentation run in docs/evidence/benchmark-instrumentation-invalid.json is intentionally invalid and was taken while Blender was rendering; it is not the final performance result. Run the final sample with Blender idle.
