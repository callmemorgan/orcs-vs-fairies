The main guard preserves account transitions if all preceding work stays intact. Undefined to null clears defaults and issues no inventory request. Null to A, A to B, and logout then A still increment the account epoch, reset the campaign reward, clear accountLoadouts, reapply appearance, invalidate old tool requests, and refresh the new signed-in account. Keeping these checks prevents stale profile callbacks from restoring the previous account's local equipment. The guard does not change hosted loadouts or the hosted cosmetics request guards.

The guard alone does not discard queued refreshes. CosmeticTools.refresh sets queuedRefresh when busy (src/ui/CosmeticTools.ts:52). reset increments requestEpoch and clears profile/catalog but leaves queuedRefresh true. run.finally drains queuedRefresh without checking the epoch of the action that queued it (line 43). A permitted sequence is an in-flight A refresh, an account change to B that resets and queues B's refresh, then logout that resets again and skips the guarded refresh. When A finishes, its stale result is ignored, but finally starts the surviving queued request under the anonymous current session. This is a source-inferred race, not a reproduced cause of the recorded errors.

Queue clearing is not included in the authorized draft. I assessed it only to explain the limitation: reset precedes a current-account refresh, so clearing previous queued work would still allow a new signed-in account's refresh to queue afterward. The initial automatic request path has no prior queue. The reviewed main.ts guard prevents that direct startup request; it does not promise that rapid account transitions cannot cause a later queued request. It also cannot cancel a request already issued or prevent a server session from expiring between a known signed-in state and a request. Those legitimate 401 paths remain.

Explicit anonymous opening and Refresh still invoke run(refresh) (src/ui/CosmeticTools.ts:44–45). A current 401 clears profile/catalog, disables equipment choices, and displays the existing sign-in message (lines 27,40). No anonymous catalog browsing is documented. There is a separate UI limit: reset does not clear message or rules text (line 52). With the main guard, losing the session while Cosmetics stays open can leave a prior success message above cleared, disabled choices until explicit Refresh or reopen. An explicit opening that races the first null session observation can also have its request invalidated without a replacement request, leaving no sign-in message. These are static UI concerns and were not observed in the modes report. They do not justify issuing a protected request after known-null logout. The draft should not claim an immediate sign-in prompt for an already-open panel. Manual request and 401 handling remain unchanged; no expanded UI account gating is part of the reviewed change.
