The installed Playwright Core 1.63.0 URL-based CDP attachment disconnects when browser.close() runs. Its two explicitly created guest contexts can be closed by their own CDP IDs. This source review resolves those dependency semantics for the hashed installed bytes; native Chromium lifetime remains the launcher's separate responsibility.

The package entry points lead to lib/coreBundle.js. The public CDP method at lines 63361–63400 returns a browser whose close forwards through the channel/dispatcher to server Browser._close (62784–62795, 55437–55440, 52689–52700). URL attach installs synthetic browserProcess.close/kill = doClose (43080–43155). That handler awaits WebSocket closeAndWait, then removes Playwright-owned temporary artifacts. Transport close is _ws.close() (39609–39618); the bundled WebSocket implementation sends a close frame and ends its network socket (utilsBundle.js:12985–13007). Temporary cleanup uses fs.promises.rm (coreBundle.js:8343–8347). This path sends neither the native CDP Browser.close command nor an OS signal to Chromium, and it does not reap the external process. chromium.launch uses a different native shutdown path.

browser.newContext sends Target.createBrowserContext with disposeOnDetach:true and stores its explicit ID (coreBundle.js:38379–38396). Closing that returned context sends Target.disposeBrowserContext for that ID, removes only its context bookkeeping and closes its pages (38749–38764). The producer uses two returned newContext handles (verify-human-wave-r3.mjs:297–300, 449–453) and closes those handles before the attachment (537–538). The inherited default CDP context has no ID; its close disposition is close-browser, which disconnects the attachment (coreBundle.js:38749–38752, 51919–51921). This distinction matters when interpreting the cleanup receipt's browserClosed field: here it means the Playwright attachment closed.

The current smaller PIDFD candidate, run-minimal63-pidfd-r3.py, requests start_new_session=True for direct Chromium launch (322), verifies SID=PID (342), and fixes its argv at 505–508. The installed Python subprocess implementation passes start_new_session into _fork_exec (/usr/lib/python3.14/subprocess.py:1919–1929). Local setsid documentation says fork children inherit their parent's session ID and exec preserves it (/usr/share/man/man2/setsid.2.gz, decompressed lines 53–57). This proves the ordinary inheritance rule and the wrapper's requested/checkable direct-child relationship. It does not prove that every Chromium helper avoids setsid, or that every listed crash-reporting flag is recognized by the later bound Chromium executable. The argv contains headless, shared-memory, crash-reporting, localhost CDP and fresh-profile switches; none is a static session-containment guarantee.

The PIDFD variant records its native closure evidence as direct unreaped roots and bound observed original-session descendants only, with unobservedDescendantsExcluded=false (483–485), and separately requires root native-lifetime admission before audit (607–612). That practical scope fits this review. No every-helper or atomic no-descendants claim is required or made.
