Context ownership changes the operation. CDP attachment supplies persistent options (43126–43135), and CRBrowser.connect creates the default CRBrowserContext with an undefined context id (38369–38375); absence of an id marks it persistent (51568–51569). Client context.close sends the channel close request (62620–62629), and its dispatcher forwards to server context.close (54421–54422). CRBrowserContext.doClose returns `close-browser` for the no-id default context (38749–38752); the base context routes that disposition to browser.close (51919–51921). Closing this default context therefore disconnects the whole attachment rather than disposing only an inherited default context. It should not be treated as a task-owned isolated context. The close path first dismisses tracked beforeunload dialogs (38750; 13345–13349), so it can affect an inherited page before disconnection. Unknown preexisting target context ids also fall back to the default-context model (38423–38430); that mapping does not establish caller ownership.

An explicit `browser.newContext()` follows the creation path (62685–62713), sends `Target.createBrowserContext` with `disposeOnDetach: true`, receives a distinct id and stores it (38379–38396). Its context.close sends `Target.disposeBrowserContext` for that id, then removes that context's bookkeeping (38749–38764). That is a real CDP request to dispose the created context and its pages. Explicit context close also flushes traces and cleans tracked downloads before internal completion (51904–51932); it remains separate from browser process termination. Disconnecting the attachment can also cause Chromium to dispose these explicitly created contexts because they requested disposeOnDetach. This review did not exercise that behavior.
