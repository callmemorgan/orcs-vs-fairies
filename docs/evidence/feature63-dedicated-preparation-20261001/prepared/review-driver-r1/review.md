## Findings

### High: descendant discovery can signal an unrelated process or miss an owned child

`Children.refresh()` builds its parent and session ownership maps from numeric PIDs at [driver/run-minimal63-r1.py:266](/home/morgana/.codex/worktrees/assembled-allied-ai/feature63-dedicated-wrapper-readiness-r1/driver/run-minimal63-r1.py:266). Its `sessions` map retains every direct child's PID as a session ID without checking that the original child identity is still alive. After a child and its session exit, Linux may reuse that PID for an unrelated process that creates a session. The unrelated process then matches the stale numeric session ID at [driver/run-minimal63-r1.py:277](/home/morgana/.codex/worktrees/assembled-allied-ai/feature63-dedicated-wrapper-readiness-r1/driver/run-minimal63-r1.py:277), passes the candidate checks if it is not PID 1063 and does not hold the protected socket, and receives a registered pidfd. A later cleanup can signal it.

The parent lookup has a related race because `parents` is a snapshot of numeric PIDs. The code does not revalidate the recorded parent identity when it assigns a newly found child. `stop_family()` also stops discovering as soon as its known records disappear, then asserts only those known records are gone at [driver/run-minimal63-r1.py:317](/home/morgana/.codex/worktrees/assembled-allied-ai/feature63-dedicated-wrapper-readiness-r1/driver/run-minimal63-r1.py:317) through [driver/run-minimal63-r1.py:343](/home/morgana/.codex/worktrees/assembled-allied-ai/feature63-dedicated-wrapper-readiness-r1/driver/run-minimal63-r1.py:343). A child created after the last refresh and before its parent exits can be absent from the final assertion.

This breaks the packet's claim that every signaled process has proven ownership and that all owned descendants are closed. Use a dedicated cgroup or another kernel-backed membership boundary that cannot be reassigned through PID reuse, and prove that boundary is empty before reporting closure. Stale PID, PPID, or session numbers are not enough.

### Medium: the collector cadence permits catch-up bursts

The collector issues a query, then waits until `started + queryOrdinal` at [collect-launched-waves-r6.py:267](/home/morgana/.codex/worktrees/assembled-allied-ai/ai-online-only-retry-readiness-r1/feature63-human-wave-composition-r1/passive-collector-r1/collect-launched-waves-r6.py:267). If a query and its file work take longer than one second, the next deadline is already past and another query starts with no delay. The 300-query and 300-second caps still hold, but the code does not guarantee a one-second minimum interval between query starts.

If "one-second cadence" means at most one query in any second, compute the next deadline from the previous query start or completion. If absolute scheduled cadence with catch-up is acceptable, root should record that interpretation because it is weaker than the packet's plain-language claim.
